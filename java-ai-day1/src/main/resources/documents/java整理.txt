list相关面试
	List接口核心特性：
     * 1. 有序集合（插入顺序）
     * 2. 允许重复元素
     * 3. 支持索引访问
     * 4. 可以包含null元素
 	ArrayList底层实现：
     * 1. 基于动态数组
     * 2. 默认初始容量：10
     * 3. 扩容机制：原容量的1.5倍
     * 4. 线程不安全
    LinkedList底层实现：
     * 1. 基于双向链表
     * 2. 每个节点包含前驱、后继引用和数据
     * 3. 不需要扩容
     * 4. 线程不安全
    Vector特点：
     * 1. 线程安全的动态数组
     * 2. 方法使用synchronized修饰
     * 3. 默认扩容为原容量2倍（可指定增量）
     * 4. 性能较低，不推荐使用
	CopyOnWriteArrayList特点：
     * 1. 线程安全的List
     * 2. 写时复制机制
     * 3. 读操作无锁，性能高
     * 4. 写操作加锁，复制新数组
     * 5. 适合读多写少的场景


  时间复杂度对比：
     *
     * 操作         ArrayList       LinkedList
     * get(index)    O(1)            O(n)
     * add(E)        O(1) 摊销       O(1)
     * add(index,E)  O(n)            O(n)
     * remove(index) O(n)            O(n)
     * remove(E)     O(n)            O(n)

  使用场景：

    ArrayList使用场景：
     * 1. 频繁的随机访问
     * 2. 尾部添加和删除操作
     * 3. 内存空间相对充足
     * 4. 元素数量可预估
     *
    LinkedList使用场景：
     * 1. 频繁在头部/中间插入删除
     * 2. 不需要频繁随机访问
     * 3. 内存使用需要更灵活
     * 4. 实现队列、栈等数据结构
     *
    CopyOnWriteArrayList使用场景：
     * 1. 读多写少的并发场景
     * 2. 集合大小通常保持很小
     * 3. 不能忍受读写冲突
 arraylist 扩容过程
   扩容过程：
     * 1. 检查当前容量是否足够
     * 2. 不足时计算新容量：newCapacity = oldCapacity + (oldCapacity >> 1)
     * 3. 如果新容量仍不足，使用minCapacity

map集合面试
	Map接口核心特性：
     * 1. 存储键值对（Key-Value）
     * 2. 键不能重复，值可以重复
     * 3. 每个键最多映射到一个值
     * 4. 不同的实现类对键值对的顺序有不同的保证
    HashMap底层实现：
     * 1. 基于数组+链表/红黑树（JDK1.8+）
     * 2. 默认初始容量：16
     * 3. 默认负载因子：0.75
     * 4. 扩容机制：当size > 容量*负载因子时，扩容为原容量的2倍
     * 5. 线程不安全
	HashMap扩容过程：
     * 1. 创建一个新数组，容量为原数组的2倍
     * 2. 遍历原数组的每个桶
     * 3. 对于每个桶中的元素，重新计算在新数组中的位置
     * 4. 将元素转移到新数组
     *
     * 注意：JDK1.8优化了扩容机制，不需要重新计算hash，通过高位运算确定位置
	LinkedHashMap特点：
     * 1. 继承自HashMap
     * 2. 维护一个双向链表来记录插入顺序或访问顺序
     * 3. 可以按插入顺序或访问顺序迭代
     * 4. 线程不安全
	TreeMap特点：
     * 1. 基于红黑树实现
     * 2. 键按照自然顺序或Comparator排序
     * 3. 线程不安全
     * 4. 操作的时间复杂度为O(log n)
	ConcurrentHashMap特点：
     * 1. 线程安全的HashMap
     * 2. JDK1.7使用分段锁，JDK1.8使用CAS + synchronized
     * 3. 支持高并发访问
     * 4. 不允许null键和null值


  时间复杂度对比：
     *
     * 操作         HashMap       LinkedHashMap    TreeMap       ConcurrentHashMap
     * get(key)     O(1)          O(1)             O(log n)      O(1)
     * put(key,val) O(1) 摊销     O(1) 摊销        O(log n)      O(1)
     * remove(key)  O(1) 摊销     O(1) 摊销        O(log n)      O(1)
     *
     * 注意：HashMap在冲突严重时可能退化为O(n)，但JDK1.8后使用红黑树优化为O(log n)
使用场景
 HashMap使用场景：
     * 1. 大多数键值对存储场景
     * 2. 不需要排序
     * 3. 单线程环境或已做好同步措施
     *
     * LinkedHashMap使用场景：
     * 1. 需要保持插入顺序或访问顺序
     * 2. 实现LRU缓存
     *
     * TreeMap使用场景：
     * 1. 需要按键排序
     * 2. 需要范围查询
     *
     * ConcurrentHashMap使用场景：
     * 1. 高并发环境
     * 2. 需要线程安全的Map

HashMap的hash方法是如何实现的？为什么要这样实现？
	hash方法：(key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16)
     *
     * 目的：减少hash冲突
     * 原理：将hashCode的高16位与低16位进行异或，让高位也参与运算，增加随机性
	  // 示例：计算索引位置
        // index = (n - 1) & hash

        // 如果直接使用hashCode，那么高位变化对索引没有影响
        // 通过异或运算，让高位参与进来，分布更均匀

HashMap什么时候会转为红黑树？

	链表长度达到8
	数组容量达到64
	如果数组容量小于64，会优先扩容而不是转树

hashmap 存储过程
	HashMap的存储过程（以JDK1.8为例）可以分为以下几个步骤：
		1.计算键的哈希值：首先，通过键的hashCode()方法计算哈希值，然后通过HashMap的hash()方法（将哈希值的高16位与低16位进行异或运算）来减少哈希冲突。

		2.确定桶的位置：通过(n - 1) & hash计算得到索引位置，其中n是数组的长度。

		3.存储键值对：

			如果计算出的桶位置为空，则直接新建一个节点并放入该位置。

			如果桶位置不为空，则可能发生哈希冲突，这时需要处理：

				如果桶中第一个节点的键与要插入的键相同（通过hash和equals判断），则更新该节点的值。

				如果第一个节点是树节点（红黑树），则调用红黑树的插入方法。

				否则，遍历链表，如果找到相同的键则更新，否则在链表末尾插入新节点。在插入后，如果链表长度达到8且数组长度达到64，则将链表转换为红黑树；如果链表长度达到8但数组长度未达到64，则进行扩容。

		4.检查扩容：插入成功后，如果HashMap中键值对的数量超过阈值（容量*负载因子），则进行扩容。扩容时，数组大小变为原来的2倍，并重新计算每个键值对的位置。

concurrmenthashmap
HashMap和ConcurrentHashMap的主要区别是什么？

	线程安全性：HashMap非线程安全，ConcurrentHashMap线程安全。
	性能：HashMap在单线程下性能好，ConcurrentHashMap在多线程下性能好。
	底层实现：HashMap是数组+链表/红黑树；ConcurrentHashMap在JDK1.7使用分段锁，JDK1.8使用CAS+synchronized。
	迭代器：HashMap是快速失败，ConcurrentHashMap是弱一致性。
	null支持：HashMap支持，ConcurrentHashMap不支持。

ConcurrentHashMap的put操作是如何实现的？

	计算key的hash值。
	如果表为空，则初始化表。
	如果定位到的桶为空，则尝试用CAS插入新节点。
	如果桶不为空，且正在扩容，则帮助扩容。
	否则，对桶的头节点加synchronized锁，进行链表或树的操作。
	如果链表长度超过8，且数组长度超过64，则转换为红黑树。
	更新元素数量，并检查是否需要扩容。

HashMap在多线程环境下为什么会引起死循环？
	在JDK1.7中，HashMap扩容时，会重新计算元素的位置，并倒序插入新数组。在多线程环境下，可能形成循环链表，导致死循环。
	JDK1.8已经修复了这个问题，但是仍然不建议在多线程环境下使用HashMap，因为会有数据丢失等其它问题。

ConcurrentHashMap在扩容期间如何进行读写操作？

* 扩容期间的读写行为：
     *
     * 读操作：
     * - 正常进行，通过ForwardingNode转发到新表
     * - 不会阻塞，性能影响较小
     *
     * 写操作：
     * - 如果访问的桶已转移，直接在新表操作
     * - 如果桶未转移，协助转移后再操作
     * - 通过锁保证转移的线程安全
     *
     * 扩容协作：
     * - 多个线程可以协同转移不同的桶区间
     * - 通过transferIndex分配任务

sleep()和wait()的区别？
	* sleep() vs wait():
     *
     * 1. 所属类：
     *    - sleep(): Thread类的静态方法
     *    - wait(): Object类的实例方法
     *
     * 2. 锁释放：
     *    - sleep(): 不释放锁
     *    - wait(): 释放锁
     *
     * 3. 使用条件：
     *    - sleep(): 任何地方都可以调用
     *    - wait(): 必须在同步代码块或同步方法中调用
     *
     * 4. 唤醒方式：
     *    - sleep(): 时间到自动唤醒
     *    - wait(): 需要其他线程调用notify()/notifyAll()唤醒
     *
     * 5. 用途：
     *    - sleep(): 用于暂停当前线程的执行
     *    - wait(): 用于线程间通信

如何停止一个线程？ 1：使用标志位  2：使用中断 interrupt() 3:使用stop() - 已过时 (不推荐使用)

synchronized和ReentrantLock的区别？
	* synchronized vs ReentrantLock:
     *
     * 1. 实现机制：
     *    - synchronized: JVM层面实现，自动释放锁
     *    - ReentrantLock: JDK层面实现，需要手动释放
     *
     * 2. 功能特性：
     *    - synchronized: 基本的互斥功能
     *    - ReentrantLock: 更丰富的功能（可中断、超时、公平锁等）
     *
     * 3. 性能：
     *    - 在低竞争情况下，synchronized性能更好
     *    - 在高竞争情况下，ReentrantLock性能更好
     *
     * 4. 使用便利性：
     *    - synchronized: 使用简单，自动管理
     *    - ReentrantLock: 需要手动管理，但更灵活
     *
     * 5. 锁的获取：
     *    - synchronized: 无法中断等待
     *    - ReentrantLock: 可以尝试获取锁，可中断

什么是线程安全？如何保证线程安全？
	线程安全的定义：
     * 当多个线程访问同一个对象时，如果不用考虑这些线程在运行时环境下的调度和交替执行，
     * 也不需要进行额外的同步，调用这个对象的行为都可以获得正确的结果，那么这个对象就是线程安全的。
	线程安全的实现方式
	   1. 不可变对象 2. 线程封闭（ThreadLocal） 3. 同步控制 （加锁）4. 使用线程安全类  5. 无状态对象


线程池有几种实现方式？

	使用Executors工厂类提供的静态方法创建不同类型的线程池。
		FixedThreadPool - 固定大小线程池
		CachedThreadPool - 缓存线程池
		SingleThreadExecutor - 单线程线程池
		ScheduledThreadPool - 调度线程池
	直接使用ThreadPoolExecutor构造函数创建自定义线程池。

ThreadPoolExecutor 核心参数

	ThreadPoolExecutor的构造函数有7个核心参数：

	corePoolSize：核心线程数。

	maximumPoolSize：最大线程数。

	keepAliveTime：非核心线程闲置超时时长。

	unit：keepAliveTime的时间单位。

	workQueue：任务队列，保存等待执行的任务。

	threadFactory：线程工厂，用于创建线程。

	handler：拒绝策略，当任务队列已满且线程数达到最大时，如何处理新任务。

拒绝策略有：

	AbortPolicy：默认，直接抛出RejectedExecutionException。

	CallerRunsPolicy：用调用者所在线程来执行任务。

	DiscardPolicy：丢弃任务，不抛出异常。

	DiscardOldestPolicy：丢弃队列中最旧的任务，然后重新尝试执行。

线程池的工作流程

	提交任务后，如果当前线程数小于corePoolSize，则创建新线程执行任务。

	如果当前线程数达到corePoolSize，则将任务放入workQueue。

	如果workQueue已满，且当前线程数小于maximumPoolSize，则创建非核心线程执行任务。

	如果当前线程数达到maximumPoolSize，且workQueue已满，则执行拒绝策略。


默认线程池有什么缺点？
	默认线程池的主要缺点：
	  FixedThreadPool/SingleThreadExecutor：
		无界队列导致内存溢出风险
		无法控制任务提交速度
	  CachedThreadPool：
		可能创建大量线程耗尽系统资源
		线程空闲时间过长浪费资源
	  ScheduledThreadPool：
		无界队列和线程数限制问题
		任务执行时间影响调度准确性
	共性问题：
		缺乏合适的拒绝策略
		无法监控和动态调整
		线程命名不友好，调试困难
	生产环境建议：
		使用ThreadPoolExecutor自定义线程池
		设置合理的有界队列
		配置合适的拒绝策略
		实现线程池监控
		根据业务特点分类使用不同线程池

如何避免死锁？
  死锁产生的四个必要条件
     1. 互斥条件：资源不能被共享，只能由一个线程使用
     2. 请求与保持条件：线程已持有资源，又请求其他资源
     3. 不剥夺条件：线程已获得的资源在未使用完之前不能被强制剥夺
     4. 循环等待条件：若干线程形成头尾相接的循环等待资源关系
  死锁预防策略
	1. 破坏请求与保持条件：一次性申请所有资源
	2. 破坏不剥夺条件：允许剥夺资源
	3. 破坏循环等待条件：按顺序申请资源

jvm

JVM内存区域

	程序计数器：   当前线程所执行的字节码的行号指示器。每个线程都有独立的程序计数器。
	Java虚拟机栈： 每个线程有一个私有的栈，随着线程的创建而创建。栈中存放着栈帧，每个方法执行时会创建一个栈帧，用于存储局部变量表、操作数栈、动态链接、方法出口等信息。
	本地方法栈：   与虚拟机栈类似，但是为Native方法服务。
	堆：           是JVM中最大的一块内存区域，被所有线程共享。几乎所有的对象实例都在堆上分配。
	方法区：       用于存储已被虚拟机加载的类信息、常量、静态变量、即时编译器编译后的代码等数据。在JDK 8之前，方法区被称为永久代（PermGen），JDK 8及之后改为元空间（Metaspace），并使用本地内存。

垃圾回收
  常见的垃圾回收算法有哪些？

	标记-清除算法：分为标记和清除两个阶段。首先标记所有需要回收的对象，然后统一回收。缺点：效率不高，会产生内存碎片。

	复制算法：将内存分为两块，每次只使用其中一块。当这一块内存用完了，就将还存活的对象复制到另一块上，然后清理掉已使用的内存。缺点：内存利用率低。

	标记-整理算法：标记过程与标记-清除一样，但后续不是直接清理，而是让所有存活的对象向一端移动，然后清理掉边界以外的内存。

	分代收集算法：当前商业虚拟机都采用这种算法。根据对象存活周期的不同将内存划分为几块，一般是新生代和老年代。新生代中，每次垃圾收集时都有大量对象死去，只有少量存活，使用复制算法。老年代中对象存活率高，使用标记-清除或标记-整理算法。

  垃圾收集器

	Serial收集器：单线程，进行垃圾收集时，必须暂停所有工作线程（Stop The World）。新生代采用复制算法，老年代采用标记-整理算法。

	ParNew收集器：Serial收集器的多线程版本，新生代使用复制算法，老年代使用标记-整理算法。

	Parallel Scavenge收集器：新生代收集器，使用复制算法，并行的多线程收集器，目标是达到一个可控制的吞吐量。

	Serial Old收集器：Serial收集器的老年代版本，单线程，使用标记-整理算法。

	Parallel Old收集器：Parallel Scavenge的老年代版本，多线程，使用标记-整理算法。

	CMS收集器：一种以获取最短回收停顿时间为目标的收集器。基于标记-清除算法，运作过程包括：初始标记、并发标记、重新标记、并发清除。其中初始标记和重新标记需要Stop The World。

	G1收集器：面向服务端应用的垃圾收集器。将堆划分为多个Region，通过可预测的停顿时间模型，来避免全局停顿。步骤包括：初始标记、并发标记、最终标记、筛选回收。（JDK1.9之后默认）

类加载机制
  类加载的过程是什么？

	类加载的过程包括加载、连接（验证、准备、解析）、初始化。

		1.加载：通过类的全限定名获取定义此类的二进制字节流，将字节流所代表的静态存储结构转化为方法区的运行时数据结构，在内存中生成一个代表这个类的Class对象，作为方法区这个类的各种数据的访问入口。

		2.验证：确保Class文件的字节流中包含的信息符合当前虚拟机的要求，并且不会危害虚拟机自身的安全。

		3.准备：为类变量（静态变量）分配内存并设置初始值（零值）。

		4.解析：将常量池内的符号引用替换为直接引用的过程。

		5.初始化：执行类构造器<clinit>()方法的过程，真正开始执行类中定义的Java程序代码。

         * 目的：确保Class文件符合规范，不会危害虚拟机安全
         */
    // 准备阶段
        /**
         * 准备阶段：
         * - 为类变量分配内存并设置初始值（零值）
         * - 静态final变量在此阶段直接赋值
         *
         * 示例：
         * public static int value = 123;     // 准备阶段：value = 0
         * public static final int CONST = 123; // 准备阶段：CONST = 123
         */
    // 解析阶段
        /**
         * 解析阶段：
         * - 将符号引用替换为直接引用
         * - 符号引用：以一组符号描述所引用的目标
         * - 直接引用：直接指向目标的指针、相对偏移量或句柄
         */
    // 初始化阶段
        /**
         * 初始化阶段：
         * - 执行类构造器<clinit>()方法
         * - <clinit>()由编译器自动收集类变量的赋值动作和静态代码块生成
         * - 虚拟机会保证父类的<clinit>()先执行
         */

  双亲委派模型
	双亲委派模型是类加载器的一种工作模式。当一个类加载器收到类加载请求时，它首先不会自己去尝试加载这个类，而是把这个请求委派给父类加载器去完成，
	每一个层次的类加载器都是如此，因此所有的加载请求最终都应该传送到顶层的启动类加载器中。
	只有当父加载器反馈自己无法完成这个加载请求（它的搜索范围中没有找到所需的类）时，子加载器才会尝试自己去加载。
	优势：避免重复加载，确保核心类的安全（比如Object类由启动类加载器加载，不会被子加载器重写）。

	 /**
     * 双亲委派模型：
     *
     * 类加载器层次：
     * 1. 启动类加载器 (Bootstrap ClassLoader)
     * 2. 扩展类加载器 (Extension ClassLoader)
     * 3. 应用程序类加载器 (Application ClassLoader)
     * 4. 自定义类加载器 (Custom ClassLoader)
     */
  双亲委派过程
	/**
    * 双亲委派工作过程：
    * 1. 收到类加载请求时，先检查是否已加载
    * 2. 未加载则委托给父加载器
    * 3. 父加载器无法完成时，自己尝试加载
    *
    * 优点：
    * - 避免重复加载
    * - 保证核心类库安全
    * - 保证类的唯一性
    */
	打破双亲委派
	  方式：
       重写loadClass()方法
       使用线程上下文类加载器

  如何判断对象是否存活？
	* 对象存活判断方法：
     *
     * 1. 引用计数法：
     *    - 给对象添加引用计数器
     *    - 有引用时计数器+1，引用失效时-1
     *    - 计数器为0时对象可回收
     *    - 缺点：无法解决循环引用问题
     *
     * 2. 可达性分析算法：
     *    - 通过GC Roots对象作为起点
     *    - 从这些节点向下搜索，路径称为引用链
     *    - 不在任何引用链上的对象可回收
     *
     * GC Roots包括：
     *    - 虚拟机栈中引用的对象
     *    - 方法区中类静态属性引用的对象
     *    - 方法区中常量引用的对象
     *    - 本地方法栈中JNI引用的对象
     *    - 同步锁持有的对象
     *    - 虚拟机内部引用（类加载器等）

 内存溢出和内存泄漏的区别？
	内存溢出：指程序在申请内存时，没有足够的内存空间供其使用。比如堆内存溢出（OutOfMemoryError）。
	内存泄漏：指程序在申请内存后，无法释放已申请的内存空间。一次内存泄漏似乎不会有大的影响，但内存泄漏堆积后的后果就是内存溢出。

  对象分配过程
	* 对象分配流程：
         * 1. 新对象尝试在Eden区分配
         * 2. Eden区空间不足时，触发Minor GC
         * 3. 存活对象移动到Survivor区
         * 4. 对象在Survivor区经历多次GC后，年龄达到阈值（默认15）进入老年代
         * 5. 大对象直接进入老年代
         * 6. 老年代空间不足时，触发Full GC

spring bean 生命周期
  实例化（Instantiation）
     创建Bean的实例。这一步主要是通过反射调用构造方法来完成。
  属性赋值（Populate）
     为Bean的属性赋值，即依赖注入。这一步会处理@Autowired、@Resource等注解。
  初始化（Initialization）
	 调用Bean的初始化方法，或者执行一些后置处理器的操作。这个阶段包括：
		调用Aware接口的方法（如BeanNameAware、BeanFactoryAware等）
		执行BeanPostProcessor的postProcessBeforeInitialization方法
		调用InitializingBean的afterPropertiesSet方法
		调用自定义的init-method方法
		执行BeanPostProcessor的postProcessAfterInitialization方法
  销毁（Destruction）
	当容器关闭时，会调用Bean的销毁方法。包括：
		调用DisposableBean的destroy方法
		调用自定义的destroy-method方法

Bean 生命周期的执行顺序是怎样的？
	1. 实例化（构造方法）
	2. 属性赋值（依赖注入）
	3. BeanNameAware.setBeanName()
	4. BeanFactoryAware.setBeanFactory()
	5. ApplicationContextAware.setApplicationContext()
	6. BeanPostProcessor.postProcessBeforeInitialization()
	7. @PostConstruct
	8. InitializingBean.afterPropertiesSet()
	9. 自定义init-method
	10. BeanPostProcessor.postProcessAfterInitialization()
	11. Bean准备就绪，可以使用
	12. @PreDestroy
	13. DisposableBean.destroy()
	14. 自定义destroy-method

BeanPostProcessor 和 BeanFactoryPostProcessor 的区别？

	特性	 		BeanPostProcessor	         	BeanFactoryPostProcessor
	作用目标		Bean 实例						Bean 定义（BeanDefinition）
	执行时机		Bean 初始化前后					Bean 工厂初始化后，Bean 实例化前
	修改内容		修改 Bean 实例					修改 Bean 的配置元数据
	使用场景		代理、包装、增强 Bean			修改 Bean 定义，如属性值、作用域等

如何优雅地管理 Bean 的生命周期？
	使用 @PostConstruct 进行轻量级初始化
	实现 InitializingBean 进行复杂的初始化逻辑
	使用 @PreDestroy 进行资源清理
	对于外部资源，实现 DisposableBean
	利用 BeanPostProcessor 进行横切关注点处理
	为不同的作用域选择合适的生命周期策略

Spring ioc
什么是控制反转（IoC）和依赖注入（DI）？它们之间有什么关系？
	控制反转（IoC）：是一种设计原则，用来将对象的创建和绑定从程序代码中转移出去，由外部容器来负责。通俗来讲，就是由容器来控制对象之间的依赖关系，而不是由代码直接控制。
	依赖注入（DI）：是实现IoC的一种方式。它是指由容器在运行时动态地将依赖关系注入到组件中。依赖注入有三种方式：构造器注入、setter注入和接口注入。
	关系：IoC是一种思想，而DI是这种思想的一种实现方式。Spring框架通过依赖注入来实现控制反转。
Spring IoC容器有哪些？它们有什么区别？
	Spring提供了两种IoC容器：
	BeanFactory：是Spring最基础的IoC容器，提供了完整的IoC服务支持。它采用延迟初始化，只有在使用到某个Bean的时候才会初始化该Bean。
	ApplicationContext：是BeanFactory的子接口，提供了更多企业级功能，如国际化、事件发布、资源访问等。它在容器启动时就会初始化所有的单例Bean（除非设置为延迟初始化）。
	通常，在大多数应用中，我们使用ApplicationContext。
Spring Bean的作用域有哪些？
	Spring Bean的作用域包括：
		singleton：默认作用域，每个Spring IoC容器中一个Bean定义对应一个对象实例。
		prototype：一个Bean定义对应多个对象实例，每次获取都会创建一个新的实例。
		request：一次HTTP请求中，一个Bean定义对应一个实例。仅在Web环境中有效。
		session：一个HTTP Session中，一个Bean定义对应一个实例。仅在Web环境中有效。
		application：一个ServletContext中，一个Bean定义对应一个实例。仅在Web环境中有效。
		websocket：一个WebSocket会话中，一个Bean定义对应一个实例。仅在Web环境中有效。


spring 循环依赖
	Spring通过三级缓存解决单例Bean的循环依赖：
	解决流程:
	// 以 ServiceA ←→ ServiceB 为例说明解决过程

	// 步骤1：创建ServiceA
	// - 实例化ServiceA（调用构造方法）
	// - 将ServiceA的ObjectFactory放入三级缓存
	// - 开始属性注入，发现需要ServiceB

	// 步骤2：创建ServiceB
	// - 实例化ServiceB（调用构造方法）

spring aop

	AOP（面向切面编程）：是一种编程范式，旨在将横切关注点（如日志、事务、安全等）从业务逻辑中分离出来，提高模块化。
	通过预编译方式和运行期动态代理实现程序功能的统一维护。Spring AOP使用动态代理（JDK动态代理和CGLIB）在运行时生成代理对象；
Spring AOP中的通知（Advice）类型有哪些？
	Before：在连接点之前执行的通知。
	After：在连接点之后执行的通知（无论连接点是否正常执行完成）。
	After-returning：在连接点正常执行完成后执行的通知。
	After-throwing：在连接点抛出异常后执行的通知。
	Around：包围连接点的通知，可以在连接点前后自定义行为，并决定是否执行连接点。

spring事务
Spring事务的传播行为有哪些？
	PROPAGATION_REQUIRED：如果当前没有事务，就新建一个事务；如果已经存在一个事务，则加入到这个事务中。这是默认设置。
	PROPAGATION_SUPPORTS：支持当前事务，如果当前没有事务，就以非事务方式执行。
	PROPAGATION_MANDATORY：使用当前的事务，如果当前没有事务，就抛出异常。
	PROPAGATION_REQUIRES_NEW：新建事务，如果当前存在事务，把当前事务挂起。
	PROPAGATION_NOT_SUPPORTED：以非事务方式执行操作，如果当前存在事务，就把当前事务挂起。
	PROPAGATION_NEVER：以非事务方式执行，如果当前存在事务，则抛出异常。
	PROPAGATION_NESTED：如果当前存在事务，则在嵌套事务内执行；如果当前没有事务，则执行与PROPAGATION_REQUIRED类似的操作。

Spring事务的隔离级别有哪些？

	ISOLATION_DEFAULT：使用后端数据库默认的隔离级别。
	ISOLATION_READ_UNCOMMITTED：读未提交，允许读取未提交的数据变更，可能导致脏读、幻读和不可重复读。
	ISOLATION_READ_COMMITTED：读已提交，允许读取并发事务已经提交的数据，可以防止脏读，但是幻读和不可重复读仍可能发生。
	ISOLATION_REPEATABLE_READ：可重复读，对同一字段的多次读取结果都是一致的，除非数据是被本身事务自己所修改，可以防止脏读和不可重复读，但幻读仍可能发生。
	ISOLATION_SERIALIZABLE：可串行化，最高的隔离级别，完全服从ACID的隔离级别，确保防止脏读、不可重复读以及幻读。

@Transactional注解的工作原理是什么？
	@Transactional注解可以标注在类或方法上。当Spring容器检测到该注解时，它会为这个Bean创建一个代理对象，
	在调用该Bean的方法时，代理对象会拦截方法调用，在方法执行前开启事务，在方法执行后根据是否抛出异常来提交或回滚事务。
	注意：@Transactional注解默认只对运行时异常（RuntimeException）和Error进行回滚，受检异常（Checked Exception）不会导致回滚。可以通过设置rollbackFor属性来改变。
Spring事务失效的常见场景
	1. 事务方法非public修饰
		解决方案：将方法改为public。
	2. 事务方法被同类中的其他方法调用
		解决方案：
			将事务方法放到另一个类中（推荐）
			使用AspectJ模式的事务管理（编译时织入或加载时织入），这样不通过代理，但配置复杂
			通过获取当前类的代理对象来调用（不推荐，且需要开启暴露代理）
	3. 事务的传播行为设置不当
	解决方案：根据业务需求设置正确的传播行为。
	4. 异常被捕获且未抛出
	解决方案：在catch块中抛出运行时异常，或者指定回滚的异常类型。
	5. 异常类型非回滚异常 (默认情况下，只有运行时异常和Error才会回滚，如果抛出的是检查异常，默认不会回滚。)
	解决方案：使用@Transactional的rollbackFor属性指定回滚的异常类型。

Spring 事务在哪些情况下会失效？

	方法非public - Spring AOP只能代理public方法
	自调用问题 - 同类方法调用不走代理
	异常被捕获 - 异常未被抛出到事务拦截器
	检查异常 - 默认只对RuntimeException回滚
	数据库引擎 - 如MySQL的MyISAM不支持事务
	传播行为配置 - 如NOT_SUPPORTED会挂起事务
	多数据源未指定 - 未明确指定事务管理器
	final/static方法 - 无法被代理

如何排查事务失效问题？
	排查步骤：
		检查方法是否为public
		确认是否是自调用
		检查异常是否被正确抛出
		验证@Transactional配置（rollbackFor、propagation等）
		确认数据库引擎支持事务
		检查多数据源配置
		使用调试工具查看事务状态

如何保证事务的可靠性？

springMVC
Spring MVC的工作流程是怎样的？
	1. 用户发送请求到前端控制器（DispatcherServlet）。
	2. DispatcherServlet收到请求后，调用HandlerMapping，找到处理请求的Controller。
	3. HandlerMapping将找到的Controller返回给DispatcherServlet。
	4. DispatcherServlet调用HandlerAdapter，由HandlerAdapter调用具体的Controller方法。
	5. Controller方法执行完成后，返回一个ModelAndView对象。
	6. HandlerAdapter将ModelAndView返回给DispatcherServlet。
	7. DispatcherServlet将ModelAndView传给ViewResolver，进行视图解析。
	8. ViewResolver解析后返回具体的View对象。
	9. DispatcherServlet对View进行渲染（将模型数据填充到视图中）。
	10. DispatcherServlet将渲染后的视图返回给用户。

Spring Boot的自动配置是如何工作的？
	Spring Boot的自动配置通过@EnableAutoConfiguration注解开启。它利用Spring的条件化配置（@Conditional系列注解）来检查类路径、已存在的Bean、属性配置等条件，满足条件时自动配置相应的Bean。
	自动配置的原理：
	Spring Boot在启动时扫描类路径下的META-INF/spring.factories文件，该文件中列出了自动配置类。
	然后根据条件注解（如@ConditionalOnClass、@ConditionalOnMissingBean等）来决定是否启用该自动配置类。
	自动配置类中通过@Bean注解创建Bean，并利用条件注解控制这些Bean的创建。

服务熔断、服务降级
服务熔断和服务降级的区别是什么？
	服务熔断：是一种故障保护机制，当服务调用失败率达到阈值时，熔断器打开，后续请求直接返回错误，不再调用远程服务。目的是防止故障蔓延和资源耗尽。
	服务降级：是一种主动降级策略，在系统资源紧张或非核心服务故障时，暂时关闭非核心服务，或者以简单的方式处理请求，保证核心服务的可用性。降级可以发生在客户端，也可以发生在服务端。
	两者关系：服务熔断后，通常会执行服务降级，即返回一个降级的结果。但服务降级不一定需要熔断触发，也可以手动触发或基于其他条件触发。
服务降级有哪些常见的策略？
	常见的服务降级策略包括：
	返回默认值：如返回一个默认对象、空列表等。
	返回缓存数据：如果之前有缓存，返回缓存的数据。
	返回兜底数据：提前准备好的静态数据。
	异步处理：将请求放入队列，稍后处理，先返回一个“处理中”的状态。
	调用备用服务：如果有备用服务，可以调用备用服务。

Hystrix 工作流程：
	构建 HystrixCommand 或 HystrixObservableCommand
	执行命令
	同步：execute()
	异步：queue()
	响应式：observe()/toObservable()
	检查熔断器状态
	检查线程池/队列/信号量 是否已满
	执行具体业务逻辑 或 调用降级方法
	计算健康度 并更新熔断器状态

nacos热部署原理
 其核心原理可以概括为：客户端通过长轮询机制监听配置变化，并在配置变更时，结合Spring的发布-订阅模型动态刷新应用上下文
   长轮询机制：这是Nacos实现实时性的关键。客户端会向Nacos服务端发起一个长轮询请求，请求的超时时间默认为30秒。服务端收到请求后：
		如果配置没有发生变化，服务端会暂时"挂起"这个请求，直到配置发生变化或者接近30秒超时，才返回响应。
		如果配置在此期间发生变化，服务端会立即结束挂起，返回变更的配置信息。
		客户端收到响应后，会立即再次发起一个新的长轮询请求，从而形成一个持续的监听。这种机制相比简单的短轮询，减少了大量无意义的请求，并在保证实时性的同时降低了服务端压力。
   事件驱动与配置刷新：
		当客户端通过长轮询得知配置变更并拉取到最新内容后，内部的ClientWorker会处理这些新配置。
		随后，NacosContextRefresher会通过Spring的ApplicationContext.publishEvent()方法发布一个RefreshEvent事件。
		这个事件会触发Spring Cloud Context的RefreshListener，进而刷新所有被@RefreshScope注解的Bean。
		在这个过程中，这些Bean会被销毁并重建，新的配置值（通过@Value或@ConfigurationProperties注解注入）也随之生效。


分布式服务

分布式事务

什么是分布式事务？为什么需要分布式事务？
	为什么需要分布式事务：
		数据一致性：确保跨多个服务的数据操作要么全部成功，要么全部失败
		业务完整性：复杂业务流程需要多个服务协同完成
		系统可靠性：防止部分成功导致的数据不一致问题

CAP理论和BASE理论是什么？
CAP理论：
	* C - Consistency (一致性)：所有节点看到的数据是一致的
     * A - Availability (可用性)：每个请求都能获得响应
     * P - Partition Tolerance (分区容错性)：系统在网络分区时仍能工作
     *
     * 在分布式系统中，只能同时满足其中两个
     */

    // CP系统：保证一致性和分区容错性，牺牲可用性
    // 例如：ZooKeeper、etcd

    // AP系统：保证可用性和分区容错性，牺牲一致性
    // 例如：Cassandra、DynamoDB

    // CA系统：保证一致性和可用性，牺牲分区容错性
    // 例如：单机数据库，不适合分布式环境
BASE理论：
	/*
     * BA - Basically Available (基本可用)：系统出现故障时，保证核心功能可用
     * S - Soft State (软状态)：允许系统存在中间状态
     * E - Eventually Consistent (最终一致性)：经过一段时间后，数据会达到一致
     */


  二段提交 （2pc）
	2PC通过一个协调者（Coordinator）和多个参与者（Participant）来达成一致性。
	两阶段提交分为两个阶段：准备阶段（Prepare Phase）和提交阶段（Commit Phase）。
	阶段一：准备阶段
		协调者向所有参与者发送事务内容，询问是否可以提交事务，并等待所有参与者答复。
		各参与者执行事务操作，将Undo信息和Redo信息写入日志（但并不提交事务）。
		参与者答复协调者，如果事务操作成功，则返回“同意”消息；如果事务操作失败，则返回“中止”消息。
	阶段二：提交阶段
		如果协调者收到所有参与者的“同意”消息：
		协调者向所有参与者发送“提交”命令。
		参与者收到“提交”命令后，会正式提交事务，并在提交后释放占用的资源。
		参与者向协调者发送“完成”消息。
		协调者收到所有参与者的“完成”消息后，完成事务。
		如果任何参与者在第一阶段返回了“中止”消息，或者协调者等待超时：
		协调者向所有参与者发送“回滚”命令。
		参与者收到“回滚”命令后，会利用之前写入的Undo信息回滚事务，并在回滚后释放占用的资源。
		参与者向协调者发送“回滚完成”消息。
		协调者收到所有参与者的“回滚完成”消息后，完成事务中断。
	优点：
		强一致性：2PC保证了分布式事务的强一致性，所有参与者要么都提交，要么都回滚。
		简单易懂：流程简单，易于理解。
	缺点：
		同步阻塞：在准备阶段和提交阶段，参与者都需要等待协调者的指令，在此期间，参与者占用的资源会被锁定，导致阻塞。
		单点问题：协调者在整个过程中至关重要，如果协调者发生故障，参与者将一直处于不确定状态，无法完成事务。
		数据不一致：在第二阶段，如果协调者只发送了部分提交命令，然后发生故障，会导致部分参与者提交了事务，而部分参与者没有提交，导致数据不一致。
		性能问题：由于需要多次网络通信和同步等待，2PC的性能通常较低，不适合高并发场景。

  三段提交
  三阶段提交（3PC）的原理
	三阶段提交将事务的提交过程分为三个阶段：CanCommit、PreCommit和DoCommit。它引入了超时机制来解决2PC中协调者单点故障和参与者长时间阻塞的问题。
	三个阶段：
	CanCommit阶段：
		协调者向所有参与者发送CanCommit请求，询问参与者是否可以执行事务提交。
		参与者如果认为可以执行事务，则返回Yes，否则返回No。
	PreCommit阶段：
		如果协调者收到所有参与者的Yes响应，则协调者向所有参与者发送PreCommit请求，参与者执行事务操作（但不提交），并返回Ack响应。
		如果协调者收到任何一个参与者的No响应，或者等待超时，则协调者向所有参与者发送abort请求，中止事务。
	DoCommit阶段：
		如果协调者在PreCommit阶段收到所有参与者的Ack响应，则协调者向所有参与者发送DoCommit请求，参与者正式提交事务。
		如果协调者在PreCommit阶段没有收到所有参与者的Ack响应（比如超时或收到No），则协调者向所有参与者发送abort请求，参与者中止事务。

	3PC如何解决2PC的问题：
		减少阻塞：在3PC中，参与者如果在PreCommit阶段后等待DoCommit消息超时，则默认执行提交。因为进入PreCommit阶段意味着所有参与者都已经同意提交，并且已经完成了事务的执行准备。
			这样，即使协调者出现故障，参与者也能继续提交事务，从而避免了长时间阻塞。
		单点故障问题：3PC通过引入超时机制，使得在协调者故障的情况下，参与者能够自动继续提交（在PreCommit阶段之后），从而减少数据不一致的可能性。

	三阶段提交（3PC）的优缺点
	优点：
		降低了阻塞范围：在3PC中，如果在PreCommit阶段后协调者故障，参与者会在等待超时后自动提交，从而避免了长时间阻塞。
		减少了单点故障的影响：由于超时后参与者可以自动提交，协调者故障不会导致整个系统一直阻塞。
	缺点：
		数据不一致风险：在DoCommit阶段，如果协调者只向部分参与者发送了DoCommit消息，然后发生网络分区，那么部分参与者提交了事务，而另一部分参与者因超时而自动提交，也可能出现数据不一致。
		实现复杂：3PC比2PC多了一个阶段，因此实现起来更复杂，交互次数更多，性能开销也可能更大。
		仍然无法完全保证一致性：在网络分区的情况下，3PC仍然可能出现数据不一致。

  TCC
  TCC原理
	TCC模式将业务操作分为三个阶段：
		Try阶段：尝试执行业务，完成所有业务的检查，并预留必要的资源。
		Confirm阶段：确认执行业务，真正提交事务，使用Try阶段预留的资源。Confirm阶段必须成功，不会失败。
		Cancel阶段：取消执行业务，释放Try阶段预留的资源。

		TCC模式要求每个服务实现三个操作：Try、Confirm、Cancel。
		事务协调器（通常是一个独立的组件）负责控制整个事务的流程，先调用所有服务的Try方法，
		如果所有Try都成功，则调用所有服务的Confirm方法；如果任何一个服务的Try方法失败，则调用所有服务的Cancel方法。

	TCC工作流程
		事务发起：事务协调器收到业务请求，开启全局事务。
		Try阶段：事务协调器调用所有参与服务的Try接口，参与者执行Try操作（预留资源），并返回成功或失败。
		决策：如果所有参与者的Try操作都成功，事务协调器记录事务日志，并进入Confirm阶段；如果任何一个Try操作失败，事务协调器记录事务日志，并进入Cancel阶段。
		Confirm/Cancel阶段：事务协调器调用所有参与者的Confirm或Cancel接口。参与者根据指令进行资源确认或释放。
		完成：事务协调器更新事务状态为完成。

    TCC优缺点
		优点：
			保证了分布式事务的强一致性。
			在业务层面实现，灵活性高。
			避免了长时间的资源锁定，因为Try阶段只是预留资源，Confirm阶段才真正提交，时间较短。
		缺点：
			对业务侵入性强，每个服务都需要实现三个接口。
			实现复杂度高，需要处理各种异常情况（如空回滚、幂等、悬挂等）。

  seata

	Seata 是什么？它的核心组件有哪些？
	Seata（Simple Extensible Autonomous Transaction Architecture）是一款开源的分布式事务解决方案，致力于在微服务架构下提供高性能和简单易用的分布式事务服务。
	  核心组件：
		Transaction Coordinator (TC)：事务协调器，维护全局事务和分支事务的状态，驱动全局事务的提交或回滚。它是独立的Seata服务器。
		Transaction Manager (TM)：事务管理器，定义全局事务的边界，开始全局事务、提交或回滚全局事务。TM集成在应用程序中。
		Resource Manager (RM)：资源管理器，管理分支事务处理的资源，与TC通信以注册分支事务和报告分支事务状态，并驱动分支事务的提交或回滚。RM集成在应用程序中，负责本地事务。

	  工作流程：
		TM向TC申请开始一个全局事务，TC创建一个全局事务并返回一个唯一的XID。
		通过XID，微服务调用链的上下文被传播。
		RM向TC注册分支事务，并将其纳入XID对应的全局事务。
		TM向TC发起全局事务的提交或回滚。
		TC驱动RM完成分支事务的提交或回滚。

	Seata 支持哪些分布式事务模式？请分别说明。
	Seata支持四种模式：
		AT 模式（自动事务模式）：
			原理：基于两阶段提交，通过代理数据源，在业务方法执行时自动拦截SQL，生成undo_log记录前后镜像，在第二阶段根据全局事务状态进行提交或回滚。
			适用场景：大多数场景，对业务代码无侵入。
		TCC 模式（Try-Confirm-Cancel）：
			原理：通过业务代码实现Try、Confirm、Cancel三个操作，由Seata框架驱动两阶段提交。
			适用场景：对一致性要求高，需要自定义资源操作的场景。
		Saga 模式：
			原理：长事务解决方案，每个参与者提交本地事务，出现失败时通过补偿操作回滚。
			适用场景：业务流程长、需要最终一致性的场景。
		XA 模式：
			原理：基于XA协议，利用数据库的XA能力实现分布式事务。
			适用场景：需要强一致性，且数据库支持XA协议的场景。

	详细说明 Seata AT 模式的工作原理。
	AT模式是Seata的默认模式，基于两阶段提交，但做了优化，无需数据库支持XA协议。其工作原理如下：
	第一阶段：
		解析SQL：Seata代理数据源，解析业务SQL，得到SQL类型、表、条件等信息。
		生成前镜像：根据条件查询数据，生成更新前的数据镜像（before image）。
		执行业务SQL：执行业务方的SQL。
		生成后镜像：根据条件查询数据，生成更新后的数据镜像（after image）。
		插入undo_log：将前后镜像和业务SQL相关信息写入undo_log表。
	第二阶段提交：
		异步删除undo_log：当全局事务提交时，TC异步通知各分支事务提交，RM直接删除undo_log即可。
	第二阶段回滚：
		查询undo_log：根据XID和分支事务ID查询undo_log。
		校验后镜像：将当前数据与after image对比，如果一致，说明没有脏写，执行回滚；如果不一致，需要根据配置策略处理（如人工干预）。
		回滚数据：根据before image还原数据。
		删除undo_log：删除对应的undo_log记录。
	优点：
		对业务代码无侵入。
		性能较好，全局事务提交时只需删除undo_log。
	缺点：
		需要创建undo_log表，占用额外存储。
		回滚时可能遇到脏写问题，需要根据策略处理。

在Seata中如何使用TCC模式？
	在Seata中使用TCC模式，需要以下步骤：
		1.定义TCC接口：使用@LocalTCC注解标注接口，并使用@TwoPhaseBusinessAction注解在Try方法上，指定Confirm和Cancel方法名。
		2.实现TCC接口：实现Try、Confirm、Cancel三个方法。
		3.全局事务使用：在全局事务中调用TCC服务。
	TCC模式的注意事项：
		空回滚：Try方法未执行，但Cancel方法被调用，需要处理空回滚。
		幂等性：Confirm和Cancel方法可能会被重复调用，需要保证幂等。
		悬挂：Cancel方法在Try方法之前执行，需要避免。



  基于MQ事务处理

  一、本地消息表
	本地消息表是一种经典的分布式事务解决方案，其核心思想是将分布式事务拆分为多个本地事务，然后通过消息队列和重试机制来保证最终一致性。
	步骤：
	在业务数据库中创建一张消息表，用于记录消息状态。
	事务发起方（生产者）在同一个本地事务中处理业务数据和消息表。
	然后通过一个定时任务轮询消息表，将未发送的消息发送到MQ。
	事务参与方（消费者）从MQ消费消息，并处理业务，处理成功后更新消息状态（或删除消息）。
	如果消费者处理失败，则消息会重投，直到成功为止（需要保证幂等性）。
  二、RocketMQ的事务消息
	RocketMQ提供了事务消息的功能，可以保证本地事务和消息发送的原子性。
	步骤：
	生产者发送半消息（预处理消息）到RocketMQ，此时消息对消费者不可见。
	RocketMQ返回半消息发送结果。
	生产者执行本地事务。
	根据本地事务执行结果，生产者向RocketMQ提交二次确认（Commit或Rollback）。
	如果提交Commit，则消息对消费者可见，消费者可以消费。
	如果提交Rollback，则消息会被删除。
	如果RocketMQ长时间没有收到二次确认，则会回查生产者的本地事务状态。
	生产者根据本地事务状态返回Commit或Rollback。

MQ

常用MQ工作原理
1. RabbitMQ
	RabbitMQ是一个基于AMQP（高级消息队列协议）的消息中间件，使用Erlang语言开发。
	核心概念：
		Producer：消息生产者，将消息发送到Exchange。
		Consumer：消息消费者，从Queue中获取消息。
		Exchange：接收生产者发送的消息，并根据规则将消息路由到Queue。
		Queue：消息队列，存储消息直到被消费者消费。
		Binding：Exchange和Queue之间的连接，定义路由规则。
	工作流程：
		生产者将消息发送到Exchange，并指定一个Routing Key。
		Exchange根据消息的Routing Key和Binding规则，将消息路由到一个或多个Queue。
		消费者从Queue中取出消息进行消费。
	Exchange类型：
		Direct：精确匹配Routing Key，将消息发送到绑定的Queue。
		Fanout：将消息发送到所有绑定到该Exchange的Queue。
		Topic：通过模式匹配Routing Key，将消息发送到匹配的Queue。
		Headers：通过消息头而不是Routing Key进行路由。
	特点：
		支持消息确认机制（acknowledgement）和持久化，保证消息不丢失。
		支持事务，但性能较差。
		支持多种消息协议，如AMQP、STOMP、MQTT等。
		管理界面友好，易于监控。

2. RocketMQ
	RocketMQ是阿里巴巴开源的分布式消息中间件，使用Java语言开发。
	核心概念：
		Producer：消息生产者，向Broker发送消息。
		Consumer：消息消费者，从Broker拉取消息。
		Broker：消息存储和转发服务器，负责存储消息并处理客户端的请求。
		Topic：消息的主题，用于对消息进行分类。
		NameServer：轻量级的注册中心，负责维护Broker的路由信息。
	工作流程：
		Producer启动时，从NameServer获取Broker的路由信息。
		Producer将消息发送到Broker，Broker将消息存储到对应的Topic中。
		Consumer启动时，从NameServer获取Broker的路由信息，然后从Broker拉取消息进行消费。
	特点：
		支持分布式部署，高可用。
		支持顺序消息、定时消息、事务消息。
		支持消息过滤（Tag过滤）。
		支持消息重试和死信队列。
	事务消息原理：
		Producer发送半消息（Half Message）到Broker。
		Broker存储半消息，并返回确认。
		Producer执行本地事务，并根据执行结果向Broker提交commit或rollback。
		如果Broker长时间未收到commit或rollback，会向Producer回查事务状态。
		根据事务状态，Broker将半消息投递到目标Topic或者删除。

3. Kafka
	Kafka是一个分布式流处理平台，最初由LinkedIn开发，使用Scala和Java语言开发。
	核心概念：
		Producer：消息生产者，向Broker发送消息。
		Consumer：消息消费者，从Broker拉取消息。
		Broker：Kafka集群中的每个服务器节点。
		Topic：消息的主题，用于对消息进行分类。
		Partition：Topic的分区，每个Topic可以分成多个Partition，分布在不同的Broker上。
		Replica：分区的副本，提供高可用。
		Zookeeper：存储Kafka集群的元数据，如Broker信息、Topic信息、分区信息等。
	工作流程：
		Producer根据指定的分区策略（如轮询、key哈希等）将消息发送到Topic的某个分区。
		Broker将消息存储到对应的分区中，并持久化到磁盘。
		Consumer通过拉取方式从Broker获取消息，并维护消费位移（offset）。
	特点：
		高吞吐量、低延迟。
		可扩展性：通过增加Broker可以水平扩展。
		持久性：消息持久化到磁盘，并支持备份。
		容错性：支持副本机制，当节点失败时自动切换。
		支持流处理：Kafka Streams。
	分区和副本：
		每个Topic可以分成多个分区，分区可以分布在不同的Broker上。
		每个分区可以有多个副本，其中一个为Leader，其他为Follower。
		生产者将消息发送到Leader副本，消费者也从Leader副本读取消息。
		Follower副本从Leader副本同步数据，当Leader副本失效时，会从Follower副本中选举新的Leader。

1：为什么要使用消息队列？
	消息队列主要用于解耦、异步和削峰。
		解耦：将系统间的直接调用改为通过消息队列间接通信，降低系统耦合度。
		异步：非核心流程异步化，提高系统响应速度。
		削峰：抵御突发流量，保护后端系统，避免被压垮。

问题2：消息队列有什么优缺点？
  优点：
	解耦、异步、削峰。
	提高系统扩展性和可维护性。
  缺点：
	系统复杂性增加：需要保证消息队列的高可用，处理消息丢失、重复消费等问题。
	数据一致性：分布式事务问题。
	运维成本：需要维护消息队列集群。

问题3：如何保证消息队列的高可用？
	RabbitMQ：
		普通集群模式：多个节点共享元数据，但队列内容只存在于一个节点，其他节点通过元数据指向该节点。此模式不能保证高可用，因为队列节点宕机会导致队列不可用。
		镜像集群模式：队列的内容会在多个节点间同步，每个节点都有完整的消息。当某个节点宕机时，其他节点可以继续提供服务。通过设置策略，可以自动将队列镜像到多个节点。
	Kafka：
		Kafka集群由多个Broker组成，每个Topic分为多个Partition，每个Partition有多个副本（Replica），
		分布在不同的Broker上。其中一个副本为Leader，其他为Follower。当Leader宕机时，会从Follower中选举新的Leader。

2. 消息丢失问题
问题4：如何防止消息丢失？
	从三个环节考虑：生产者、MQ自身、消费者。
	生产者：
		开启确认机制（如RabbitMQ的publisher confirm，Kafka的ack机制）。
		失败重试。
	MQ自身：
		持久化消息（如RabbitMQ将消息和队列持久化，Kafka将消息持久化到磁盘）。
		集群部署，多副本机制。
	消费者：
		关闭自动确认，改为手动确认（如RabbitMQ的manual ack，Kafka手动提交offset）。
		确保消息被成功处理后再确认。

问题5：RabbitMQ如何保证消息不丢失？
	生产者：开启publisher confirm机制，确保消息到达Broker。
	Broker：将消息和队列都设置为持久化（durable）。
	消费者：关闭autoAck，使用手动确认，确保消息被成功处理后再ack。

问题6：Kafka如何保证消息不丢失？
	生产者：设置acks=all（或-1），表示所有副本都收到消息才认为发送成功。
	Broker：设置副本因子（replication.factor）至少为3，最小同步副本（min.insync.replicas）至少为2。
	消费者：关闭自动提交offset，处理完消息后手动提交offset。

3. 重复消费问题
问题7：如何解决重复消费问题？
	重复消费通常是由于消费者在处理消息后，没有及时提交确认（如offset）导致的。
	解决方案：
		保证消息处理的幂等性。即无论消息被消费多少次，结果都一样。
		通过业务逻辑实现幂等，
		例如：
			使用数据库唯一键：插入数据时使用唯一键，重复插入会失败。
			使用Redis set：将消息ID存入Redis，消费前检查是否已存在。
			使用版本号：更新数据时带版本号，通过乐观锁避免重复更新。

问题8：如何保证消息的幂等性？
以订单支付为例：
在支付成功后，会发送一条支付成功的消息。消费者需要根据订单ID处理支付成功的逻辑。
在消费消息时，先查询订单的支付状态，如果已经支付，则直接确认消息，不再处理。
或者，在更新订单状态时，使用条件更新：update order set status='paid' where id=123 and status='unpaid'。

4. 顺序消息问题
问题9：如何保证消息的顺序性？
	Kafka为例：
		Kafka保证同一个Partition内的消息顺序性。
		将需要保证顺序的消息发送到同一个Partition（比如使用同一个Key）。
		消费者使用单个线程消费这个Partition，或者使用线程池但保证同一个Key的消息由同一个线程处理。

	RabbitMQ为例：
		一个队列只有一个消费者，自然顺序消费。但这样性能低。
		如果需要多个消费者，可以将需要顺序的消息发送到同一个队列，然后使用单个消费者消费。

5. 消息积压问题
问题10：如何解决消息积压问题？
	先定位积压原因：是消费者消费速度慢，还是生产者生产速度过快。
	临时紧急处理：
		增加消费者数量（如增加消费线程，或者增加消费节点）。
		先批量获取消息，然后异步处理，提高吞吐量。
		如果消息不重要，可以丢弃。
	长期优化：
		优化消费者业务逻辑，提高消费速度。
		评估消息队列的容量，增加分区和副本，提高整体吞吐量。

6. 技术选型问题
问题11：Kafka和RabbitMQ的区别？
	架构：RabbitMQ是传统的消息队列，基于AMQP协议；Kafka是分布式流式处理平台，基于自己的协议。
	性能：Kafka的吞吐量更高，适合大数据场景；RabbitMQ吞吐量相对较低，但延迟更低。
	功能：RabbitMQ支持丰富的消息模式（如工作队列、发布订阅、路由、主题等），支持消息确认、事务等；Kafka主要支持发布订阅，支持持久化、流处理。
	使用场景：RabbitMQ适合企业级应用、实时消息；Kafka适合日志收集、流处理、大数据分析。

7. 其他问题
问题12：消息队列如何实现延迟消息？
	RabbitMQ为例：
		使用死信队列（DLX）和TTL实现延迟消息。将消息发送到一个设置了TTL的队列，消息过期后变成死信，然后被路由到另一个队列，消费者从这个队列消费。
	RocketMQ为例：
		支持延迟消息，在发送消息时设置延迟级别（如1s、5s、10s等）。
	Kafka不支持延迟消息，需要自己实现，例如：
		将消息按照延迟时间放入不同的Topic（如按分钟分Topic），消费者轮询这些Topic。

问题13：如何设计一个消息队列？
	可以从以下几个角度考虑：
	持久化：消息是否持久化，如何存储（文件、数据库等）。
	投递保证：至少一次、至多一次、精确一次。
	高可用：集群模式，主从复制，选举机制。
	顺序性：如何保证消息顺序。
	延迟消息：如何支持延迟消息。
	事务消息：如何支持事务。
	扩展性：如何支持水平扩展。

常用redis的数据结构
字符串（strings）、哈希（hashes）、列表（list）、集合（set）、有序集合（sorted set）

redis持久化方式  RDB 和 AOF
Redis提供两种持久化机制：RDB（Redis DataBase）和AOF（Append Only File）。
  RDB：
	原理：在指定的时间间隔内，将内存中的数据集快照写入磁盘。
	优点：
		适合大规模的数据恢复。
		对数据完整性要求不高的场景。
		性能高，fork子进程进行持久化，主进程不进行IO操作。
	缺点：
		最后一次持久化后的数据可能丢失（因为间隔时间内的数据未持久化）。
		当数据量很大时，fork过程可能会很耗时，造成服务器在毫秒级别内停止处理请求。
  AOF：
	原理：以日志的形式记录每个写操作，重启时通过重新执行这些命令来恢复数据。
	优点：
		数据丢失少，可以配置每秒同步一次，最多丢失一秒的数据。
		AOF文件易于解析，可以直接操作。
	缺点：
		AOF文件体积通常比RDB大。
		恢复速度慢。

 缓存穿透  查询不存在的数据，绕过缓存直接访问数据库    解决方案1：缓存空对象         解决方案2：布隆过滤器

redis 主从模式。哨兵模式
Redis主从复制是如何工作的？
	Redis主从复制是指将一台Redis服务器的数据，复制到其他的Redis服务器。前者称为主节点（master），后者称为从节点（slave）。数据的复制是单向的，只能由主节点到从节点。
	工作流程：
		从节点执行SLAVEOF <master_ip> <master_port>命令，向主节点发起连接。
		从节点向主节点发送SYNC命令。
		主节点收到SYNC命令后，开始执行BGSAVE命令生成RDB文件，并使用缓冲区记录此后执行的所有写命令。
		主节点BGSAVE执行完后，将RDB文件发送给从节点，从节点载入RDB文件，将数据同步到从节点。
		主节点将缓冲区的写命令发送给从节点，从节点执行这些命令，达到数据最终一致。
		后续同步：主节点会持续将写命令发送给从节点，保证主从数据一致性。
	特点：
		主从复制是异步的，所以从节点可能会延迟同步。
		从节点可以接受其他从节点的连接，形成链式复制。
		主从复制不会阻塞主节点，在同步数据时，主节点可以继续处理命令。

7. Redis哨兵模式
问题7：Redis哨兵模式是什么？有什么作用？
	Redis哨兵（Sentinel）是Redis官方提供的高可用性解决方案。它由一个或多个Sentinel实例组成的系统，可以监视多个主节点以及它们的所有从节点，并在主节点下线时自动进行故障转移。
	作用：
		监控：Sentinel会不断检查主节点和从节点是否运作正常。
		提醒：当被监控的某个Redis节点出现问题时，Sentinel可以通过API向管理员或者其他应用程序发送通知。
		自动故障转移：当一个主节点不能正常工作时，Sentinel会开始一次自动故障转移操作，它会将失效主节点的其中一个从节点升级为新的主节点，并让其他从节点改为复制新的主节点。
	故障转移过程：
		多个Sentinel实例检测到主节点下线。
		选举一个Sentinel作为领导者来进行故障转移。
		Sentinel领导者选择一个从节点作为新的主节点。
		向其他从节点发送命令，让它们复制新的主节点。
		将旧的主节点设置为从节点，当它重新上线时，它会成为新的主节点的从节点。

8. Redis集群
问题8：Redis集群的原理是什么？
	Redis集群是Redis的分布式解决方案，通过分片（sharding）来进行数据共享，并提供复制和故障转移功能。
	数据分片：
		Redis集群使用哈希槽（hash slot）来分片，一共有16384个哈希槽。
		每个键都属于这些哈希槽中的一个，通过CRC16(key) mod 16384来计算键key属于哪个槽。
		集群中的每个节点负责一部分哈希槽。
	节点：
		集群由多个节点组成，每个节点都是一个Redis实例。
		节点之间通过 Gossip 协议进行通信，每个节点都保存着整个集群的状态信息。
	故障转移：
		集群中的节点通过投票机制来检测节点是否下线。
		如果主节点下线，则从它的从节点中选举一个作为新的主节点。
	客户端与集群交互：
		客户端可以连接集群中的任意节点，如果请求的键不在该节点负责的哈希槽中，节点会返回MOVED错误，并告诉客户端正确的节点。
		客户端可以根据MOVED错误信息重定向到正确的节点。

索引
1. 索引是什么？
	答：索引是帮助MySQL高效获取数据的数据结构（通常是B+树）。它可以类比于书籍的目录，能够快速定位到数据所在的位置，从而加快查询速度。
2. 索引的优缺点？
	优点：
		大大加快数据的检索速度。
		通过创建唯一性索引，可以保证数据库表中每一行数据的唯一性。
		在使用分组和排序子句进行数据检索时，同样可以显著减少查询中分组和排序的时间。
	缺点：
		创建索引和维护索引需要耗费时间，这种时间随着数据量的增加而增加。
		索引需要占用物理空间，除了数据表占数据空间之外，每一个索引还要占一定的物理空间。
		当对表中的数据进行增加、删除和修改的时候，索引也要动态的维护，这样就降低了数据的维护速度。

3. 索引的类型？
	普通索引：最基本的索引，没有任何限制。
	唯一索引：索引列的值必须唯一，但允许有空值。如果是组合索引，则列值的组合必须唯一。
	主键索引：一种特殊的唯一索引，不允许有空值。
	组合索引：多个列上创建的索引，只有在查询条件中使用了创建索引时的第一个字段，索引才会被使用。
	全文索引：主要用来查找文本中的关键字，而不是直接与索引中的值相比较。
4. 如何创建索引？
	sql
	-- 创建普通索引
	CREATE INDEX index_name ON table_name (column1, column2, ...);
	-- 创建唯一索引
	CREATE UNIQUE INDEX index_name ON table_name (column_name);
	-- 创建主键索引（通常在创建表时指定）
	ALTER TABLE table_name ADD PRIMARY KEY (column_name);
5. 什么情况下应该创建索引？
	在经常需要搜索的列上创建索引，可以加快搜索的速度。
	在作为主键的列上，强制该列的唯一性和组织表中数据的排列结构。
	在经常用在连接的列上，这些列主要是一些外键，可以加快连接的速度。
	在经常需要根据范围进行搜索的列上创建索引，因为索引已经排序，其指定的范围是连续的。
	在经常需要排序的列上创建索引，因为索引已经排序，这样查询可以利用索引的排序，加快排序查询时间。
	在经常使用在WHERE子句中的列上面创建索引，加快条件的判断速度。

6. 什么情况下不应该创建索引？
	表记录太少。
	经常增删改的表（因为需要维护索引，降低更新速度）。
	数据重复且分布均匀的列，例如性别、国籍等（因为索引的选择性太低，可能不会产生优化效果）。

7. 索引失效的情况？
	使用LIKE时以通配符开头（'%abc'）会导致索引失效，但是以通配符结尾（'abc%'）不会。
	在索引列上进行运算、函数操作等。
	使用OR连接条件，如果OR前后的条件中有一个列没有索引，那么涉及到的索引都不会被使用。
	不符合最左前缀原则的组合索引。
	如果MySQL估计使用全表扫描比使用索引快，则不使用索引（例如数据量很小的表）。

8. 最左前缀原则是什么？
	答：最左前缀原则指的是，如果创建的是组合索引，那么查询条件中必须包含索引中最左列，才能使用到该索引。例如，创建了组合索引(a, b, c)，那么查询条件中必须包含a，才能使用这个索引。如果查询条件中只有b和c，则不会使用这个索引。

9. 如何查看索引是否被使用？
	答：使用EXPLAIN命令可以查看SQL语句的执行计划，从而判断是否使用了索引。主要看key字段，它表示实际使用的索引。

10. 如何优化索引？
	避免创建过多的索引，只对常用的查询条件创建索引。
	尽量使用覆盖索引（索引包含了查询中需要的所有字段），避免回表操作。
	使用短索引，如果字符串列很长，可以只索引前几个字符。
	定期分析表，使用ANALYZE TABLE来更新索引的统计信息，帮助优化器选择更好的索引。

11. B树和B+树的区别？
	B树中每个节点都存储数据，而B+树只有叶子节点存储数据，非叶子节点只存储键值。
	B+树的叶子节点之间有指针相连，便于范围查询。
12. 什么是覆盖索引？
	答：如果一个索引包含（或覆盖）所有需要查询的字段的值，我们就称之为覆盖索引。覆盖索引可以避免回表操作，提高查询性能。

13. 什么是回表？
	答：回表是指通过索引查找到主键值后，还需要根据主键值回到主键索引（聚簇索引）中再查找整行数据的过程。覆盖索引可以避免回表。

14. 聚簇索引和非聚簇索引的区别？
	聚簇索引：将数据存储与索引放到了一块，索引结构的叶子节点保存了行数据。一个表只能有一个聚簇索引，通常是主键索引。
	非聚簇索引：将数据与索引分开存储，索引结构的叶子节点指向了数据对应的位置。非聚簇索引的叶子节点存储的是主键值，所以通过非聚簇索引查询数据需要回表。

15. 如何选择索引的数据类型？
	尽量使用数据类型小的列作为索引，因为索引本身也占空间，小的数据类型可以让更多的索引进入内存，提高效率。
	使用简单的数据类型，例如整型比字符串类型更简单，因为整型的比较操作更快。
	避免使用NULL，建议设置NOT NULL，因为NULL值会使索引、索引统计和值比较都更复杂。

16. 索引下推（Index Condition Pushdown）是什么？
	答：索引下推是MySQL 5.6引入的优化，可以在索引遍历过程中，对索引中包含的字段先做判断，直接过滤掉不满足条件的记录，减少回表次数。

17. 如何监控索引的使用情况？
	答：可以通过SHOW INDEX命令查看索引的基数（Cardinality）等信息，也可以使用SHOW STATUS查看索引的使用频率。此外，MySQL的performance_schema和sys库也提供了很多索引使用的统计信息。

18. 为什么使用B+树作为索引结构？
	B+树的磁盘读写代价更低：内部节点不存储数据，因此一个节点可以存储更多的键值，树的高度更低，查询时IO次数更少。
	B+树的查询效率更加稳定：所有数据都存储在叶子节点，所以每次查询都需要从根节点到叶子节点，路径长度相同。
	B+树更有利于范围查询：叶子节点之间有指针相连，范围查询只需要遍历叶子节点。

19. 什么是前缀索引？
	答：前缀索引是指对字符串的前几个字符建立索引。这样可以减小索引大小，提高索引速度。但是，前缀索引不能用于排序和分组操作，并且选择性可能会降低。

20. 如何创建前缀索引？
	sql
	CREATE INDEX index_name ON table_name (column_name(length));
	选择长度的原则是：选择足够长的前缀以保证较高的选择性，同时又不能太长以节省空间。

21. 如何删除索引？
	sql
	DROP INDEX index_name ON table_name;
22. 索引的 Cardinality 是什么？
	答：Cardinality 指的是索引中不重复值的数量的估计值。这个值越大，索引的选择性越好。如果 Cardinality 很小，那么索引可能效果不好。

23. 如何更新索引的 Cardinality？
	答：使用ANALYZE TABLE table_name命令可以更新索引的 Cardinality 统计信息。

24. 什么是联合索引？为什么要使用联合索引？
	答：联合索引是指对多个列创建的索引。使用联合索引可以避免回表，提高查询效率，并且可以支持多列排序和查询。

25. 联合索引的顺序如何选择？
	将选择性高的列放在前面，这样能够更有效地过滤数据。
	考虑查询的频率和顺序，尽量使常用的查询条件能够利用索引。
26. 什么是索引合并？
	答：索引合并是MySQL对多个索引分别进行条件扫描，然后将结果合并。通常发生在对多个列进行OR操作，或者对多个索引进行AND操作时。但是，索引合并的效率往往不如一个联合索引。
27. 如何强制使用某个索引？
	sql
	SELECT * FROM table_name FORCE INDEX (index_name) WHERE ...;
28. 如何忽略某个索引？
	sql
	SELECT * FROM table_name IGNORE INDEX (index_name) WHERE ...;
29. 什么是全文索引？如何使用？
	答：全文索引是一种用于全文搜索的索引类型，主要用于文本字段。在MySQL中，可以使用MATCH ... AGAINST语法进行全文搜索。
30. 如何优化排序操作？
	为排序的列创建索引，这样可以利用索引的有序性避免排序操作。
	如果排序操作无法避免，尝试增加sort_buffer_size参数的大小。
31. 什么是索引的选择性？如何计算？
	答：索引的选择性是指不重复的索引值（Cardinality）与表记录数（#T）的比值。选择性越高，索引的效率越高。计算方式为：选择性 = Cardinality / #T。
32. 如何查看表的索引信息？
	sql
	SHOW INDEX FROM table_name;
33. 如何判断一个查询是否使用了覆盖索引？
	答：使用EXPLAIN命令，如果Extra列显示Using index，则表示使用了覆盖索引。
34. 什么是隐式类型转换？它对索引有什么影响？
	答：隐式类型转换是指当查询条件中的数据类型与列的数据类型不一致时，MySQL会自动进行类型转换。这可能会导致索引失效。
35. 如何避免隐式类型转换？
	确保查询条件中的数据类型与列的数据类型一致。
	在编写SQL语句时，使用正确的数据类型。

36. 什么是索引的碎片？如何整理？
	答：索引的碎片是指由于数据的插入、删除和更新操作导致索引页分裂和不连续，从而降低索引的效率。可以通过OPTIMIZE TABLE table_name命令来整理表的碎片。
37. 什么是延迟关联？
	答：延迟关联是一种优化技巧，通过使用覆盖索引先获取主键，然后再根据主键获取数据，从而避免回表操作。常用于分页查询中。
38. 如何优化大表的索引？
	避免在更新频繁的列上创建索引。
	使用分区表。
	定期分析和优化表。

39. 什么是索引的倾斜？如何解决？
	答：索引的倾斜是指索引中的某些值出现的频率非常高，导致查询这些值的时候效率很低。可以通过修改查询条件，或者使用联合索引来避免。
40. 如何检查重复索引？
	答：可以使用pt-duplicate-key-checker工具来检查重复索引。
41. 什么是自适应哈希索引？
	答：自适应哈希索引是InnoDB引擎的一个特性，当某些索引值被频繁访问时，InnoDB会在内存中基于B+树索引再创建一个哈希索引，以加快访问速度。
42. 如何禁用自适应哈希索引？
	答：可以通过设置innodb_adaptive_hash_index=0来禁用自适应哈希索引。
43. 什么是索引的排序规则？如何选择？
	答：索引的排序规则是指索引中字符的比较规则。在选择时，应该与查询条件的排序规则一致，否则可能导致索引失效。
44. 如何创建降序索引？
	答：在MySQL 8.0中，可以指定索引的排序顺序。例如：
	sql
	CREATE INDEX index_name ON table_name (column_name DESC);
45. 什么是函数索引？如何创建？
	答：函数索引是指对列使用函数表达式创建的索引。在MySQL 8.0中，可以创建函数索引。例如：
	sql
	CREATE INDEX index_name ON table_name ((UPPER(column_name)));
46. 如何监控索引的读写次数？
	答：可以通过performance_schema库中的table_io_waits_summary_by_index_usage表来监控索引的读写次数。
47. 什么是索引的覆盖扫描？
	答：索引的覆盖扫描是指查询只需要通过索引就可以获取所有需要的数据，而不需要回表。
48. 如何优化大表的索引创建？
	答：可以使用ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE来在线创建索引，避免锁表。
49. 什么是索引的统计信息？如何更新？
	答：索引的统计信息是MySQL优化器用来选择索引的依据。可以通过ANALYZE TABLE命令来更新。
50. 如何查看索引的大小？
	答：可以通过SHOW TABLE STATUS命令查看表的大小，其中包括索引的大小。

事务
事务的ACID特性是什么？
	原子性（Atomicity）：事务是一个不可分割的工作单位，事务中的操作要么都发生，要么都不发生。
	一致性（Consistency）：事务必须使数据库从一个一致性状态变换到另一个一致性状态。
	隔离性（Isolation）：多个事务并发执行时，一个事务的执行不应影响其他事务的执行。
	持久性（Durability）：一旦事务提交，则其所做的修改将会永久保存在数据库中。

二、事务隔离级别
3. MySQL有哪几种事务隔离级别？
	MySQL支持四种隔离级别，由低到高分别为：
	读未提交（Read Uncommitted）：允许读取尚未提交的数据变更。
	读已提交（Read Committed）：只能读取已经提交的数据。
	可重复读（Repeatable Read）：同一事务中多次读取同一数据的结果是一致的。
	串行化（Serializable）：最高的隔离级别，完全服从ACID的隔离级别，所有事务依次逐个执行。

5. 不同隔离级别会引发哪些并发问题？
	脏读（Dirty Read）：一个事务读取了另一个事务未提交的数据。发生在读未提交隔离级别。
	不可重复读（Non-repeatable Read）：同一事务中，多次读取同一数据，由于其他事务的更新操作导致数据不一致。发生在读未提交和读已提交隔离级别。
	幻读（Phantom Read）：同一事务中，多次查询同一范围的数据，由于其他事务的插入操作导致结果集不一致。发生在读未提交、读已提交和可重复读隔离级别。

MVCC的工作原理。
	MVCC通过为每行数据维护多个版本来实现并发控制。
	在InnoDB中，每行记录都有两个隐藏列：创建版本号和删除版本号。
	每个事务在开始时都会得到一个唯一的事务ID（版本号）。
	在可重复读隔离级别下，MVCC通过以下方式工作：
		SELECT：只查找版本早于当前事务ID的行，并且该行在事务开始之前未被删除。
		INSERT：为新插入的行记录当前事务ID为创建版本号。
		DELETE：为删除的行记录当前事务ID为删除版本号。
		UPDATE：相当于DELETE+INSERT，旧行记录删除版本号，新行记录创建版本号。
